# RUNNING SCGSERVER

`scgserver <config>` connects to the broker its config names, reads commands from the
command topic and publishes what it is doing. `scgcommander <config>` takes the same
config, so it reaches the same broker and topics, and sends the commands typed at its
prompt.

Three things have to run: a broker, the server, and the commander.

## The broker

~~~bash
cd tools/mosquitto-broker
docker compose up
~~~

This can be on another machine. The address that matters is the one the clients connect
to, so put it in `broker_host` of the config:

~~~json
"broker_host": "10.1.2.40",
~~~

## The test document

`TEST_SETUP` names a TSD, and every step of the TSD names its rid by an absolute url,
`file://` or `http://`. An absolute url only holds on the machine it was written for, so
the tsds under `assets/tsd` work on the stage machine only. Elsewhere write one next to the
rids it plays.

A step has to be at least as long as the rid it plays, and
`test-rid-sisi-stage-1.json` is ten seconds long.

~~~bash
cat > /tmp/tsd.json <<'TSD'
{
    "name": "sisi stage 1",
    "description": "one step, playing one rid",
    "steps": [
        {
            "duration_seconds": 10.0,
            "interference": "file:///home/sagax/sgx/scg/assets/rid/test-rid-sisi-stage-1.json"
        }
    ]
}
TSD
~~~

The steps play one after the other. Rids whose gap is shorter than `start_ahead_s` of the
config are merged into one part and have to configure the radios the same way. A longer
gap starts a new part, which may configure the radios differently. The gap runs from the
end of one rid to the start of the step of the next one. Every part is played by a
pipeline of its own, the streams are closed between parts and the radios stay open. The
rids of the whole TSD have to be of the same version.

`scglint tsd <config> <url>` reads the tsd and every rid it names, merges them into parts
and validates every part, which is the same work the server does when the command arrives.
Running it first turns a failure at test time into a message now.

## A run

~~~bash
# terminal 1, the server
cd build-sidekiq
./scgserver ../assets/config/sisi-stage-mock.json

# terminal 2, the commander
cd build-sidekiq
./scgcommander ../assets/config/sisi-stage-mock.json
> testsetup file:///tmp/tsd.json 2026-09-21T16:10:00+02:00 1
> teststart 1
~~~

`sisi-stage-mock.json` sets `mock_radios`, so nothing is transmitted and no hardware is
needed, and every radio of a rid is reported with a warning. `sisi-stage-live.json` is the
same configuration driving the radios.

## Commander commands

| command | what it sends |
|---|---|
| `testsetup <tsd_url> <time> <test_id>` | TEST_SETUP |
| `teststart <test_id>` | TEST_START |
| `testcancel <test_id>` | TEST_CANCEL |
| `intstop` | INT_STOP |
| `intstart`, `testupdate`, `testend` | the commands the server reads and ignores |
| `help` | the same list |
| `quit`, `exit` | leaves |

The commander subscribes to the test and error topics as well, so the answers to what it
sends arrive in its own output. [mqtt-protocol.md](mqtt-protocol.md) has the messages.

## What happens to a test

The command is answered at once, with a reason on the error topic if it is refused. The
warnings of the checks only go to the server log. An accepted test is recorded into `recording_directory` as soon as there is room in the
queue. The server log gets a summary of the test: its start, every transmission with the
rids it plays, every gap, and its end. The pipeline of a part starts `start_ahead_s` before
the part with its output held back until the exact moment, and until the test is
authorized with TEST_START. A test that is not authorized by its start time fails. The
directory of a test is removed once it is over.

The test is `TEST_RUNNING` from the start of the TSD and `TEST_COMPLETED` at its end, and
the status messages carry those times. The signal status follows what the pipelines
actually transmit.

A gnss spoofer is generated by the ssp engine during the recording, at about one second of
work per second of signal. With `prerecord_gnss` off nothing is recorded for it, and the
engine generates it while the test plays, with one thread. It has to keep up with real
time then, which depends on the machine and the sample rate. With `mock_gnss` set in the
config the spoofer is replaced by silence instead, and a rid with one is accepted with a
warning.
